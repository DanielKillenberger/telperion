# fn-118 friction

## 2026-09-23 - worker, before the first edit

What I was doing: reading the pipeline code against the host design (Architecture, 2026-09-23) before implementing R1 to R4.

What stopped it: two places where the code contradicts the design in ways the design does not address. Both need a design call, and the dispatch rules say to stop and report NEEDS_HUMAN rather than decide.

1. Appearance traits as `described` entries have no route through `generate`. The design has the requirements table list bark colour and roughness, leaf front and back colour, and the hue and brightness ranges as `described` traits with level tables. In the code, a described trait is a `routes::ValueTable`: one scalar `dial`, one `measured_metric`, and levels holding a scalar `target_range` and scalar `candidates`. `generate::run_described` renders every candidate on that dial and reads the metric from the species measurer's `completed` event. The measurer (`crates/telperion-core/examples/species_metrics`) emits no colour, roughness, hue or brightness metric, so every appearance trait the select stage scores above `unstated` would end in `level-miss`. A colour also spans three `MaterialParams` channels (for example `bark_red/green/blue`), which a scalar level cannot hold. Open question: does an appearance trait (a) get its own copied-range route that skips render and measure, (b) get a level shape with a range for each channel and a measured colour metric, or (c) become documentation input only that select scores and generate skips?
2. `manifest::validate` runs on every stage's `Context::open` through `manifest::load`, not only when a person admits the manifest. A coverage check there refuses every existing short pipeline manifest: `catalogue/european-ash/manifest.json` (broadleaf: height and dbh only), the fn58 validation fixtures for oak and spruce (height only), and about eight inline test manifests in `tests/{pipeline_upstream,pipeline_fixes,stages_downstream,gap,routes,validation_fn30}.rs`, `src/pipeline/manifest.rs` and `src/pipeline/stage.rs`. Bringing every fixture up to the table puts roughly ten fields and six described traits through `quality`, `select` and `generate` in each test, which changes decision lists, mock-judge traffic and expected artifacts well past this spec's scope. Open question: do existing manifests migrate to the table, does the check apply only at admission (the `manifest-proposed` admit, or a new manifest `schema_version`), or do fixtures move to a growth form outside the table, which means `validate` must accept an unlisted growth form?

Also found: `catalogue/date-palm/manifest.json` is not tracked on any branch. It exists only as an untracked folder in the fn-80 worktree. Master removed the folder in #57 because the node catalogue check requires all thirteen files in every catalogue folder, so a branch that commits the manifest on its own turns that check red. The committed copy of the palm's manifest is `.flow/evidence/date-palm/pipeline/manifest.json` on fn-80 and fn-82, neither of which is in this stack.

Cost: about 25 minutes of reading and no code. What would have removed it: the design naming the route an appearance trait takes through `select` and `generate`, the migration rule for manifests that predate the table, and the path of the palm manifest on this stack.
