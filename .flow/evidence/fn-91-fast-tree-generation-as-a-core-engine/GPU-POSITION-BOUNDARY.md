# Next position-expansion boundary

This is a host design analysis, not measured implementation or acceptance. Task .6 is still implementing shared contact rings. It primarily benefits the surface-contact workload; the current oak fixtures have surfaceContact = 0 and need a different reduction.

Task .5 lowered native canonical wood preparation from 129.8/145.3 ms to 117.2/130.1 ms for oak seeds 1/7. Its exact traversal change produced 3.5% native completed-frame gain on oak 1. The earlier controlled wood-stage experiment measured vertex/attribute emission, frames and normals separately with 6.5-21.3% observer overhead; those shares identify mechanisms but do not predict a new speedup. The current code still emits every rounded wood position, checks every procedural triangle and recovers each ring radius on CPU before resident expansion.

A potential next boundary would prepare compact ring centres, frames, radii, along-distances and angular/profile inputs on CPU, then emit positions on GPU into the packed xyz buffer shared by contacts and wood. Default CPU surface/output stays available. GPU float32 arithmetic may change positions; forcing GPU emulation of CPU float64 solely to preserve bytes would defeat the owner's evolution policy. The qualification would instead require sound geometry, actual contact on the same generated GPU surface, measured spatial/normal/radius error and perceptually equivalent views. Preserve exact unaffected output checks and same-backend repeatability.

The existing wood normal kernel cannot alone prove triangle validity: a zero-area face can coexist with valid neighbouring vertex normals. A position candidate needs a lightweight validity/bounds pass before foliage reads it. Invalid or unsupported geometry must select a complete coherent fallback, never mix foliage attached to rejected wood with a different silently substituted surface. Bounds reduction must avoid six contended global atomics per vertex; use group reductions or a separate bounded reduction. Exact indices, run spans, caps and counts remain structural checks even if positions differ.

Do not allocate the full wood index/normal/attribute outputs before foliage just to validate positions. That would move hundreds of megabytes into the foliage-compute peak. Position descriptors and validity scratch should drop after their completed pass, leaving only the shared position buffer and compact CPU metadata during foliage. Final wood expansion then follows the existing order. Joint allocation/lifetime accounting must be compared with the new .6 baseline before implementation is accepted.

This boundary needs a concrete task and baseline after .6 resolves. It is a separate hypothesis from the admission-loop change and shared-input reuse, with no predicted 10x or 100 ms success. Native/browser and CPU-owned delivery qualification remain separate. The owner has authorized continued work on fn-91; a finished intermediate task is not itself a stopping condition.
