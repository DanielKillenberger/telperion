# Shared canonical contacts

Host approved this design before implementation. `surface.rs:227–290` emits sorted wood runs. An optional contact map records each distal node's lower, upper, first and last ring vertex offsets from that run's vertex base, sample count and trunk burial offset, following `surface/attachment.rs:94–103`. Caps stay outside every contact range. Ordinary surface preparation and CPU building request no map and retain their allocations.

Foliage uses the same station loop with a typed borrowed canonical position input and those edges. The default owned station API stays available. Borrowed contacts contain real float32 xyz positions, never empty placeholder geometry. This eliminates repeated ring emission and the unused attachment segment AABBs. Descriptor order and rounded coordinates remain exact even though the sorted wood runs change absolute contact indices.

Resident requests with positive surface contact prepare canonical wood first. Oak's contact is zero, so its ordering remains unchanged as a regression control. Unsupported/collapsed preparations discard their shared inputs before existing fallback. After station preparation the renderer uploads packed xyz positions once, releases CPU positions and the edge map, and retains an explicit uploaded-wood object (GPU buffer plus compact metadata). Foliage runs first; wood expansion adopts the same STORAGE/COPY_SRC/COPY_DST/VERTEX buffer. Contact WGSL reads three scalar floats instead of a padded vec4; projection math and execution order do not change.

Old CPU contact upload simultaneously retains 24 bytes per ring vertex and a 16-byte upload vector, plus edge maps/AABBs during preparation. New canonical preparation retains 12 bytes per wood vertex (including two cap vertices per run), compact wood metadata, and the optional edge map. Before foliage dispatch only compact wood metadata remains on CPU. GPU contact storage changes from 16 bytes per ring vertex to 12 bytes per wood vertex, and remains the wood position allocation. Metadata lifetime extends through foliage; that overlap must be counted against actual simultaneous peaks, not inferred from removed allocations. Compare preparation/upload, foliage expansion and wood expansion stages separately, including prior live tree buffers. Process RSS and unmeasured driver/upload scratch remain named limitations.
