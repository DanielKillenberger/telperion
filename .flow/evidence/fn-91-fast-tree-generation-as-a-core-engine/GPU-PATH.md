# GPU foliage boundary investigation

Host investigation, 2026-09-20. Design evidence, not an implemented candidate or a performance result.

The baseline makes foliage expansion worth investigating for spruce: 7,353,754 placements from 95,389 structural nodes at seed 1. Oak has 715,065 placements and 125,087 nodes. `foliage/station.rs` derives each placement from a run's cumulative distances, frames, station ordinal and random values. Those run inputs can be prepared on the CPU without expanding every leaf there. SplitMix32 advances by addition, so indexed random draws are possible; randomness alone does not require serial GPU execution. Run counts and stream offsets still need preparation.

Contact is part of placement. `surface/attachment.rs` builds swept rings and per-node edge ranges, tests the current and neighboring segments, then uses closest-point projection if the radial ray misses. A GPU candidate must implement that fallback and verify actual attachment. Uploading these rings adds substantial data beyond the node descriptions. The previous fn-12 contact misses are a correctness warning, not a reason to require historical output bytes.

The current renderer consumes packed twelve-byte leaves through `select.rs`. A useful GPU path would allocate that final storage buffer and expand into it, then let selection and drawing consume it directly. It must also provide culling, bounds and the canopy mass grid: `mass.rs` currently visits every CPU placement, and `submit::crown_of` derives the crown from them. Generating leaves on the GPU and reading all of them back for these steps would recreate the transfer problem. Small summary readback and GPU reductions are distinct from full placement readback; both still belong in latency and memory accounting.

CPU-output consumers remain a separate measurement. Their requested bytes must be delivered, including readback if a GPU implementation is used. A render-only speedup does not qualify that representation.

Memory constrains the operation order. The first GPU experiment should prepare and expand foliage before constructing the CPU wood mesh, release uploaded CPU descriptors and transient compute buffers promptly, then construct wood. A CPU-output request should read and release resident foliage before constructing wood. A rendering request should retain the final foliage buffer for direct submission. This avoids keeping a CPU wood mesh, CPU attachment data, GPU attachment data and both temporary and final leaf buffers alive together. Measure the actual peaks; this ordering is a design to test, not proof that the memory target passes. Preserve the old rendered tree until the new result has passed validation, and include it in resident-memory accounting.

Foliage alone cannot reach the accepted target on every fixture. Native oak seed 1 takes 942.79 ms, so its 10x target is 94.28 ms; wood alone takes 252.21 ms and growth 59.47 ms. Even removing all foliage work would leave more than three times the target. Native spruce seed 1 has a 558.18 ms target; its growth and wood together take about 245 ms before placement, culling, bounds and output delivery. These are bounds inferred from the baseline, not predictions of a GPU implementation.

The bounded CPU experiment first removes redundant bounds and per-station work in the shared path. Its measured outcome determines the next candidate. A GPU foliage experiment must establish total latency and completed-frame delivery before expansion into wood; no isolated shader timing can qualify it. Phone, peak-memory domains and the first-completed-frame baseline remain gaps recorded in BASELINE.md.

## First GPU experiment: host implementation contract

This is the next bounded mechanism to test after the CPU checkpoint, not a requirement to ship an unsuccessful prototype. Begin with native oak and spruce seed 1. Do not implement wood expansion or botanical growth on the GPU in this experiment. Do not reuse a previously generated specimen as a warm result; only initialized pipelines and reusable capacity may be warm.

The core prepares an engine-independent foliage description from the already generated skeleton. Its first supported parameter domain is twig placement with zero short-shoot spacing and zero limb clumping. These are capability checks, never species checks. Other valid parameters retain the CPU path with an explicit backend result. Invalid parameters still fail validation. The current pure-core CPU build remains available and receives no GPU dependency.

For supported inputs, prepare bearing runs, cumulative distances and the existing corrected segment frames. Regular twig stations need counts and ranges, not a CPU array of every station or a CPU matrix per leaf. Describe groups of stations sharing a segment, with run ordinal, output offset, endpoints, radii, frame and attachment edge range. Dispatch fixed-size tiles of these groups; do not assign a serial loop over an entire crown to one invocation. Preserve total station count, checked allocation/index arithmetic and the authored max-instance failure. A stationary run places nothing, as before. Equal distances select the same segment convention as place_run.

Each leaf derives its SplitMix32 stream position from its global pre-cull ordinal: scatter uses four draws and zero scatter uses one. Twig station generation itself consumes no random draws. WGSL performs the current radial/axis/scatter/scale calculations and packs the existing twelve-byte representation. f32 arithmetic may change bytes; it must preserve repeatability within this implementation, valid frames and visual quality. Detect nonfinite transforms and out-of-reference coordinates explicitly rather than silently wrapping or dropping them.

Upload the swept attachment rings and edge ranges once. Implement the current segment and neighboring-segment ray tests and the closest-point fallback; a circular-radius substitute is not sufficient. Surface-contact zero bypasses this data. Retain the current shell test over transformed element vertices. Mark survivors, use stable group ranks and prefix/scatter as the existing selection pipeline does, and keep the final compact packed buffer for drawing. Stable compaction avoids scheduling-dependent instance order.

Compute both placement-origin crown bounds and full transformed-element bounds on the GPU, with explicit error flags and survivor count. GPU occupancy and depth passes produce the existing canopy mass-grid layout. Mean occupancy and gap termination must retain the current lighting semantics. Read back only bounded summary data for rendering; validation may separately read placements, and CPU-output delivery must time its required full readback. No CPU loop over all GPU-generated placements may be hidden in rendering preparation.

Use the existing Foliage/Select pipelines with a resident-buffer submission entry. Reuse element uploads, level metadata and draw bindings; do not create a second renderer. A prepared result owns its asynchronous resources and is tied to the renderer/device that created it. Reject a result submitted to another renderer before mutating live state. Keep transient buffers owned until completion, release them after use, and validate device limits and generation errors before replacing the live tree. A later browser wrapper must not hold a RefCell borrow across await and must reject stale/disposed completions; browser adoption follows the native candidate result.

The native experiment measures initialized-engine time to (a) completed rendering with the resident buffer and (b) owned CPU geometry including production readback. Count skeleton generation, descriptor/contact preparation, allocations, transfers, compute, synchronization, CPU wood construction and requested delivery. A comparison mode uses the current CPU build, same renderer, camera, viewport and completion boundary. Report original native CPU-output baseline comparisons separately. Record allocation lifetimes and peak accounted CPU/GPU buffer bytes; do not equate live buffer bytes with an unmeasured whole-process peak.

Verification starts small: empty/invalid/budget cases, rotated and bent contact fixtures, deterministic repeated generation and stable compaction, finite valid geometry, and supported-parameter fallback. Check actual attachment against swept facets with a tolerance justified by packed position quantization and f32 error. Then measure one cold and three warm builds for oak and spruce seed 1. Only an end-to-end win justifies the remaining seeds and browser integration. Take at most four comparison images per capture; whole-tree and close views are needed if the candidate reaches visual qualification. Stop and report a design gap to the host rather than inventing a new system boundary.
