# After the palm: a deletion pass on the loop (owner, 2026-09-24)

The owner asked whether four days on the loop is making it an overengineered mess. The host's read: the core works (literature sets the starting values, the reviewer compares renders with photographs, tuning moves the dials, a stall names a real generator gap; fn-144 was found and fixed that way). But most of the 2026-09-24 stops were the loop guarding itself, not the palm. The owner agreed: once the palm is accepted, run a deletion pass driven by FRICTION.md, before the next species.

Proposals (the owner decides which become work):

- **Build identity means rerun, never pause.** A rebuilt binary or a changed config reruns what it touched; it never asks for a scoped decision naming `next_identity`.
- **The reviewer requalifies itself.** A change to a reviewer adapter re-freezes and replays its qualification in the same change, instead of pausing the run on "vision protocol differs from replay".
- **Tuning reads the live dial table.** The species config names exclusions only, not a frozen copy of 200+ rows.
- **The conductor stops ceremony around work that exists.** Most of the dependency state machine can go (design and implement dispatches, Jev complexity routing, after-the-fact records, `adopt`): the host and the owner decide specs anyway. Keep: dependency attached, landed at a commit, stages rerun.
- **Paid stages rerun on their inputs, not the build.** A rebuild never reruns the literature stages when sources and extraction code are unchanged.

The measure: the next species runs end to end with only real generator gaps and the owner's checklist as stops. Fewer states, fewer files and fewer decisions per run.
