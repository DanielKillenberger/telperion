## Optimizations beyond fn-102 (A-E expected byte-identical; I reorders their priority)

- **A. Cull early exit per leaf.** `cull` (`foliage.rs:253`) transforms every vertex until one lands in the shell; a deep leaf pays for all, each vertex two `powf` plus a 128-segment profile scan (`envelope.rs:221`). All vertices lie within rho = |M|*extent of the leaf origin and profile distance is 1-Lipschitz: reject when the origin is deeper than shell + rho + eps, accept when even the deepest vertex is inside the shell. Needs a slope bound for `radius_at`; the profile scan can use a height-band index. Status: open.
- **B. Cull while placing.** Placement reserves and fills a Vec for the whole crown (placement.rs:149), then `retain` drops most of it. Test each leaf as it is placed; same order, same draws. Mainly peak memory (spruce native peak 370-402 MB, fn-91 `native-peak-rss.json`). Status: open.
- **C. Forward cursor in station placement.** `station.rs:71` walks back from the run's end for every station, O(stations x segments) per run. Stations are in increasing distance, so a cursor makes it linear. Likely part of the spruce's 3,845 ms placement (82.5% of its build); share unmeasured. Status: open.
- **D. Attractor grid in growth.** `scaffold.rs:194-220` `pull`/`consume` scan every attractor per step; `AttractorGrid` exists but only the unused `colonize` path uses it. Matters most for the slim package (289-649 ms, missed its 250 ms goal). Byte-identical only if candidates are visited in index order. Status: open.
- **E. Parallel cull.** Core is single-threaded except the wood surface (Linux x86_64, >= 250k vertices). Cull is per-leaf independent and byte-identical in parallel. Parallel placement needs per-run seeded streams, a byte change the 2026-09-20 policy allows with evidence; second step. Status: open.
- **F. Wasm flags.** No `simd128`, no threads. SIMD is a one-measurement experiment; threads need COOP/COEP on the host page, a product decision. Status: open.
- **G. Renderer preparation.** Five GPU round-trips per resident tree; CPU delivery computes masses and drops them (compute.rs:217, preparation.rs:289); wood expansion waits for foliage compute; rings and segments copied twice (compute.rs:57, data.rs:86). Status: open.

- **H. Wood and leaf outputs in parallel.** Both read only the skeleton and plan, so native builds can run them on two threads and join, byte-identical, reporting the wood's error first. Gain is the shorter of the two (oak ~45%, spruce ~5%, birch ~8% on the CPU path); none in Wasm without threads. On the GPU path the matching overlap is CPU wood while the GPU places leaves, and submitting GPU wood expansion with the leaf compute (see G). Status: decided (owner, 2026-09-23), part of fn-102, as the pipeline's scheduling principle: the stages form a dependency graph; each runs once, when its inputs are ready; stages independent of each other run in parallel; unrequested stages never run. Conditions: output never depends on timing (own random streams, fixed join order, errors reported in stage order); the gain and the peak memory are measured under R4, since the wood surface already uses up to 8 threads; the same graph runs serially where there are no threads (Wasm), so parallelism is never needed for correctness. Applied as R8.
- **I. GPU expansion is the generator's, and the drawn default.** Owner decision, 2026-09-23: consumers are GPU applications and should receive the full-fidelity tree to draw, never reimplement leaf expansion; generation must be fast, so the GPU is the drawn path. The core owns expansion of the plan into leaves and wood as a contract: the plan's data layout, portable shaders (WGSL, translatable through naga to HLSL/GLSL/MSL/SPIR-V), and a CPU reference expander that defines correct, matched by the GPU within tolerance under the 2026-09-20 policy. Stages 1-3 stay on the CPU. Needs station forms for short shoots, limb clumping, no twig layer, lobed crown surfaces and the numeric fallback before it can be the only drawn path. Its own spec after fn-102. Consequence: A-C become CPU-consumer work (tests, reference, no-GPU consumers), lower priority. Status: decided in direction; spec not written.

## Proposed order

Amend fn-102 (1-4, possibly H), implement it; then the GPU expansion contract (I) as the main performance spec, with G folded into it; A-C (and E) as a CPU-reference hot-path spec at lower priority; D when the slim package or growth latency needs it.
