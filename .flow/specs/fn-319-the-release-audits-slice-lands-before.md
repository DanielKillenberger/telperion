# The release audit's slice lands before the tag

## Why

Codex's release audit of 26 Oct 2026 (`.flow/evidence/fn-237-release-the-tree-space-engine-replaces/AUDIT-2026-10-26.md`, NEEDS_WORK) found defects on the release branch after killenberger.com reported slower trees than 0.1.4. The owner chose what 0.2.0 takes (26 Oct: audit packages 1, 3, 4 and 5; 27 Oct: the floret reduction, "i think we should fix it. We want high quality 0.2.0"). Matching 0.1.4's per-tree speed is not required (fn-285); the site's warm-up (package 2) is killenberger.com's. The five parts are independent and ship in one tag, so they are one spec (owner, 27 Oct).

## Requirements

- **R1 (field startup; audit package 1):** the field prepares only the programs it dispatches. Today `web/field.rs` `fields()` calls `Generator::prepare_programs` (`generation/resident.rs:46`), which also makes `crate::curve::passes` (eleven surfacing passes), and `resident/build.rs` `Tools::new` makes the `Sweeper` and `Ringer` the field never dispatches (`resident/field/make.rs` reads no curve). The renderer's preparation keeps every program it dispatches. Proof: a paired cold measurement of preparation and first tree before and after, in the browser and natively; field answers byte-equal before and after on every shipped preset; the renderer's compile test still passes. Deleting the field's use of the renderer's tool set was tried before making it cheaper.
- **R2 (validation parity; audit package 3):** the device field refuses what the CPU entry refuses. Reproduced on Ordinary, seed 1, n 12: `canopy.maxInstances=1` (CPU: "foliage instance budget") and `canopy.scatter=-1` (CPU: "scatter") return a tree on the device (`resident/field/make.rs`, `placeable`). The device applies the same checks from one shared definition, not a copy. Proof: both inputs rejected through `growField` and the CPU entry, as an ordinary test.
- **R3 (typed renderer API; audit package 4):** `setTree`, `setTreeGpu`, `admission` and `beginGrowth` in `src/browser/render.ts` take a `Family` and serialize it internally with the existing wire serializer, as `TreeEngine.build` and `growField` do. The CPU field's `FieldFrame`/`FieldQuery` (`src/browser/core.ts`) and the device field's `Grid`/`FieldAnswer` (`src/field/`) get one definition. Proof: typecheck, every caller in the repository (harness, tests, docs examples) updated, the package's export test.
- **R4 (compile once, and the CI key; audit package 5):** `compileField()` with no source returns one module for concurrent and repeated calls, as 0.1.4 did (`src/field/index.ts`). `scripts/ci-key.mjs` includes `docs/parameters.md` and `src/browser/parameters.generated.ts` in the suites whose tests read them, and the workflow's path filters let a change to either through. Proof: a test that two concurrent calls resolve the same module; `ci-key.test.mjs` shows a change to either file changes the key.
- **R5 (florets reduce on the device; audit roadmap 4, fn-257 R8):** a flowering tree's field reads back only the grid. Today `resident/florets.rs` `Organ::read` reads every placed floret (12 bytes each, about 7.9 MB on Laurelin) and `resident/field/make.rs` computes `seat_bounds` and counts florets into the grid on the CPU. The bounds and the per-cell counts are computed on the device. Proof: Telperion's and Laurelin's field answers equal before and after on the same GPU (or, if the order of float sums changes bytes, the flower channel's cubes match as fn-46.4 measured them, stated with the measurement); the floret readback no longer appears in the field's transfers; time before and after recorded.

## Boundaries

Out: 0.1.4's per-tree speed (fn-285), the lean field artifact (fn-242), GPU lifetime and budget (audit roadmap 5), grow once and sample repeatedly (roadmap 6), GPU pregeneration (fn-318), the site's warm-up. No preset or botanical change. Builds on a branch off fn-198 (F4) and merges into F4; nothing is pushed or published without the owner.
