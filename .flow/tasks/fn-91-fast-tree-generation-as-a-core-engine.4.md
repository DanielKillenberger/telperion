# fn-91-fast-tree-generation-as-a-core-engine.4 Expand wood into resident GPU buffers from canonical positions

## Description
Implement the next bounded GPU candidate selected by the host from task .3. Keep parent R1-R5 unchanged; task .1 remains open. The measured opportunity is combined index/normal/attribute expansion and upload, not a normals-only kernel. This candidate targets existing native/browser GPU-resident rendering; owned CPU delivery stays on the current CPU wood builder and its .2 bounded leaf readback.

Host design:

1. Add an engine-neutral prepared surface representation in the core: canonical float32 positions in the existing run/vertex order, compact per-run/ring metadata (ring counts, vertex/index offsets, along-distance, angular values, radius metric as needed), bounds and run table. Reuse the existing path/sample/frame/vertex formula through small shared helpers; do not independently invent a second surface algorithm. The default surface::build output and allocation strategy must remain equivalent. Preparation does not allocate full index, normal, coordinate or per-vertex radius arrays. Use fallible checked reservation and existing validation/overflow errors. Empty geometry remains supported.
2. Preserve exact geometry for this first candidate. CPU preparation checks every procedural triangle with the current float64 calculation on the canonical float32 corners for finiteness and zero area. If triangles need dropping or a supported numeric case cannot safely use the GPU normal path, select the existing CPU wood builder rather than trying new GPU triangle-compaction semantics. No partial tree or silently omitted geometry. Positions, indices, winding, caps, run order/spans and bounds must match the current CPU surface on GPU-admitted fixtures. Recover each ring's radius from those rounded positions using the existing renderer radius arithmetic, store only one radius per ring (caps zero), and expand it on GPU; this preserves bark metrics.
3. Shared async GPU expansion uploads canonical positions and compact metadata once. Generate the existing procedural indices, surface coordinates, per-vertex radii and normals into final renderable buffers. Compute normals independently per vertex by gathering incident triangles in original index order, with bounded ring/cap adjacency, not float atomics or serial processing of all leaves/triangles. A workgroup-per-run with strided vertices/faces and checked 2D dispatch is acceptable; support long runs and >65535 runs. GPU normal arithmetic may differ from CPU f64, but must produce finite unit normals and meet the preselected 0.001-radian angular tolerance against CPU normals on the measured fixtures and focused geometry cases. Unusable/zero/overflow GPU normal results return a small status summary and fall back to the CPU wood builder before commit, with explicit backend reporting. A GPU validation/device failure remains a named error. Do not read back full GPU wood for resident delivery. Verification readback is outside timing.
4. Adopt final wood buffers through the existing renderer with actual VERTEX/INDEX/STORAGE/COPY usage and counts. Preserve renderer identity, old-tree behavior during pending requests, stale replacement and disposal semantics, CPU fallback and later CPU submissions. Prepared owns all resources until accepted. Check limits before GPU allocation; never truncate to fit. Store resident wood metadata separately instead of pretending empty CPU arrays are full output. Update count/fit/report paths accordingly. No species-specific renderer path. The existing browser setTreeGpu and native resident Generator share the implementation; default CPU APIs remain unchanged.
5. Extend stage/capacity reporting to distinguish CPU versus GPU wood and explicitly account prepared CPU positions/metadata, new GPU buffers and previous live tree buffers at replacement. Drop temporary CPU data and GPU metadata promptly after completion. Include staging/lifetime limitations; do not claim whole peak-memory qualification from counters alone. The GPU normal shader is a bounded follow-up to the already beneficial GPU foliage candidate, not a full GPU skeleton/wood-position rewrite.
